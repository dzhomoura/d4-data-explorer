# Chapter II — Stage 1: Paladin Paragon glyph research

## Executive summary

The pinned Diablo IV 3.2.4.74043 extraction contains **21 mechanically defined Paladin-eligible glyphs**. Fifteen are Paladin-exclusive and six are shared, including Challenger, the only Paladin-eligible starting glyph in the global list. Every eligible glyph has a Rare definition, a primary affix, an attribute-gated passive power, and a Legendary affix. Fifteen primaries convert one local core attribute into a damage bonus. Six amplify an authored node class. Each of the ten Paladin boards contains one instance of the same socket definition.

Catalogue identity, socket coordinates, affix references, authored thresholds, recipe ingredients, and Legendary destination attributes are sufficiently established for a data import and read-only previews. The data supports a progression model with radius breakpoints at 25 and 50 and strong candidates for Rare and Legendary caps of 50 and 150. Game-accurate totals depend on validating the radius mask, scalar evaluation, which node values feed the local pool, amplified Rare behavior, and combat power dispatch. In particular, Honed uses **Intelligence**, Feverous uses **Willpower**, Chip uses **Willpower** but costs **Emerald** fragments, and Judicator’s Legendary bonus applies to **Holy and Fire**.

All authoritative game-data claims use [DiabloTools/d4data at commit 75e619f0d90a0951945747f45feef59c076a5db0](https://github.com/DiabloTools/d4data/commit/75e619f0d90a0951945747f45feef59c076a5db0). Its [buildVersion.txt](https://github.com/DiabloTools/d4data/blob/75e619f0d90a0951945747f45feef59c076a5db0/buildVersion.txt) is 3.2.4.74043.

## Evidence conventions

- **VERIFIED — DATA** means an explicit pinned field, reference, formula, or string. This includes tooltip intent as written.
- **DERIVED FROM DATA** means arithmetic, a join, a classification, or an inference from those fields. Conditional calculations specify their assumptions.
- **VERIFIED — IN-GAME** requires documented gameplay observations that establish the claimed behavior. The repository contains unamplified node observations for experiment baselines. There are no matching-build glyph observations in this report.
- **EXPERIMENTALLY SUPPORTED** requires a documented but inconclusive observation. No glyph claims are assigned this classification.
- **UNRESOLVED** means an authoritative runtime rule or value remains unsupported. In this report a power’s formula and its tooltip can be verified even where its event handler is unresolved.

## Existing application boundaries

`paragon-visual/app.js` owns rendering, socket classification, selection, the allocation graph, and persistence. `board-rotation.js` projects coordinates in 90° increments, keeping the source index stable. `connected-boards.js` retains the identity `instanceId:sourceIndex` as it projects the physical layout, links only chosen facing gates, and validates connected allocations and subtree turns. Historical independent-board saves retain their own rotations, allocations and inspection contexts. Connected version 2 persists revision, attached board identities, topology, rotations and source-index allocations. Version 1 migration, Board 00 import/export, and external-attribute persistence have separate paths. Existing saves contain no glyph assignment or level.

`paragon-calculator.js` checks pinned board/node/formula identities, evaluates verified base contributions, computes totals for thresholds, and resolves conditional contributions. `paragon-bonus-registry.js` holds board-scoped, unamplified node values with raw attribute identity, unit/category and evidence provenance. `paragon-thresholds.js` binds Rare node selectors to placement indices 0–4 in connected mode and keeps the historical inspection evidence separate. `calculateConnectedBonuses` first aggregates base core across boards and then evaluates each board with the other boards’ core contributions folded into that board’s threshold context. The wrapper includes a guard for observed nonzero conditional core contributions. `totalAttributes` is threshold context and includes external attributes. `verifiedParagonBonuses` is the Paragon contribution output. The application currently charges one point for an allocated socket through its general allocation counting, and the pinned game UI instructs the player to unlock the node to access glyphs. The game’s socket point cost and refund behavior still need observation.

## Progression and numerical representation

**VERIFIED — DATA.** Every eligible glyph has `eRarity=1`, a recipe in `arUpgradeRecipes[1]`, and one Legendary affix gated at `eRequiredRarity=2`. Its primary and additional affixes have `eRequiredRarity=0`. `globals.glo.json` → `ptContent[0].arGlyphRadiusLevels` is `[0, 0, 0, 25, 50]`. In the same object `unk_8f2bc8b` is `[0, 50, 150]`, `unk_ed24ce7` is `3`, and nearby `unk_c6ea03` and `unk_331b5e0` are `1`. The schema leaves those adjacent fields unnamed. `Glyph_Upgrade.stl.json` has generic dynamic rank/cap text and legacy-looking hard-coded `RareGlyphLevelUpgrade` / `LegendaryGlyphUpgrade` values of 40 and 100, plus Magic text at 15. The strings also include an older Nightmare Dungeon XP instruction alongside Pit upgrade attempts. Their coexistence makes any one hard-coded string weak evidence for the active runtime branch.

**DERIVED FROM DATA.** A strong interpretation is level 1 as the first displayed rank, Rare through 50, a separate gem payment at the 50 boundary, Legendary through 150, and a base radius 3 growing to 4 and 5. The ordered rarity cap array, named radius array and matching recipe slots support that model. **UNRESOLVED** for exact client/off-by-one behavior. Observe 24→25 and 49→50→51 separately, including level 50 before/after the gem transaction where possible. Read the maximum from an actual same-build tooltip. Level 150 is the terminal checkpoint used for the calculations below. Level 100 remains a diagnostic checkpoint.

**VERIFIED — DATA.** `ParagonGlyphExperienceTable.gam.json`, SNO 810212, has 201 `ptData[0].tEntries` rows. `nDeltaXP` at indices 0–20 is `[1,8,15,24,35,46,59,72,87,104,121,140,159,180,203,226,251,276,303,332,361]`; indices 21–200 are zero. ### Exact formula fields and candidate runtime evaluation

**VERIFIED — DATA.** The affix schema stores float scalars and the extracted JSON preserves the underlying float32 values, including `0.15000000596046448` for a nominal 0.15. Primary amplifiers and stat mappings have two independent coefficients, `flStartingBonusScalar` and `flAddedBonusScalarPerLevel`. The three budget references have a single `arRanges[0]` each with start 0 and extracted range fields `[0,99999]`. The actual referenced `ptData[0].tEntries[i].arRanges[0].tFormula.value` expressions are:

| Index | GBID | Formula name | Source expression |
| ---: | ---: | --- | --- |
| 568 | 379537727 | `ParagonGlyphAdditive_Rare_StatMain` | `0.04 * ParagonPowerBudgetMultiplierGlyphStatBonusRare()` |
| 569 | 379761887 | `ParagonGlyphAdditive_Rare_StatSide` | `0.06 * ParagonPowerBudgetMultiplierGlyphStatBonusRare()` |
| 572 | 2549607169 | `ParagonGlyphAdditive_Rare_BonusToNodes` | `0.001` |

The pinned `arParagonPowerBudgetMultiplier` nominal values by index are `[0.01,0.025,0.02,0.05,0.04,0.05,0.04,0.15,0.05,0.033,0.10]`. The array is real, and its consumers are unresolved. Let `S=ParagonPowerBudgetMultiplierGlyphStatBonusRare()` and `T=ParagonPowerBudgetMultiplierGlyphThresholdBonusRare()`. `S=0.05` and `T=0.10` are test hypotheses. They are values present in the array and yield plausible tooltip magnitudes. There is no field-to-intrinsic binding in the extracted schema, and 0.05 occurs three times. The eligible affixes do not reference the legacy Vampiric entries (566–567/570), including the explicit `Floor` in entry 570.

**DERIVED FROM DATA / UNRESOLVED.** The numerical tables evaluate the explicit intercept and slope as `B(L)=a+b*(L-1)`, a rank-1 anchor hypothesis. They give every distinct authored coefficient pair and disclose the conversion applied. A rank-0 anchor would add one slope increment to every row. The extraction does not expose where that anchor is applied, the semantics of `unk_12a5abd` (500 for stat mappings, 100 for amplifiers and Legendary affixes, 1 for power grants), or possible runtime clamping. Therefore the displayed values in those tables are predictions. They also avoid prematurely rounding source floats, which can otherwise move a visible half-tie or a threshold boundary.

- **Operation 2, local attribute conversion.** Test `B(L) * budget * A`, where `A` is purchased local core attribute. A discrete competitor is `5*floor(A/5) * B(L) * budget`. At `A=7` they produce 1.4 and 1.0 times the five-point rate. The affix points to a source attribute and the localized text specifies five purchased points. Neither the affix nor the referenced budget formula contains a per-five floor or a local total. The final operator and order live outside those expressions.
- **Operation 1, node amplification.** Test `amp=B(L)*0.001` and `effective=base*(1+amp)`. The `0.001` is explicitly extracted. Observing known base and amplified values is needed to confirm the multiplier application, any rounding and treatment of conditional parts.
- **Operation 4, Legendary direct contribution.** Test `B(L)` as a normalized damage fraction. An authored 0.055 corresponds to 5.5 percentage points under that conversion. These records have no budget, local attribute map, threshold, or power. The rarity gate is the sole gate attached to the affix. The destination attribute still limits damage applicability.
- **Operation 5, additional passive.** The affix scalar and slope are both 0 and carry no budget. The power has its own formulas. Constants and `T` formulas have no explicit glyph-level variable or interpolation reference. The same predicted parameters apply at rank 1 if the local requirement is reachable, 25, 50, Legendary activation and 150. A separate hidden runtime level dependence remains unresolved.

**VERIFIED — DATA.** The primary and Legendary text renders `GlyphAffixScalar` using one explicit display decimal (`1%`, `1%+`, `1%x`) with plus/multiplicative conventions. Additional powers commonly render `SF_n*100` with a percent format, use raw script values for durations/counts, and Sentinel/Feverous specify a single decimal for their per-stack percentages. UI requirement numerals use string arguments. Half-tie rounding, truncation, integer conversion of amplified core attributes and whether glyphs consume displayed or unrounded values remain **UNRESOLVED**.

## Framework-independent integration recommendations

Expose a pure calculation function that takes a pinned ruleset, board instances and placement, allocated source cells, glyph assignments/rarities/ranks, and separately furnished character inputs for global thresholds. Reuse the board and threshold resolvers when the applicable runtime rules are verified. Record a diagnostic when a dependency is unresolved.

- **Unconditional contribution output** should give normalized Paragon-only flats and modifiers with one effective contribution per board instance, cell and attribute index. The diagnostic decomposition can show original base, amplification delta, active conditional and effective result. Only the effective amount should enter exported totals.
- **Local glyph output** should give the socket, radius membership, matching/allocated cells, base and effective local pools, selector state, and coefficient provenance. The pool supports inspection and should not be reapplied as character attributes.
- **Amplification output** should carry transformation source and target IDs, verified policy and exact units. The transformation modifies the owning node's contribution.
